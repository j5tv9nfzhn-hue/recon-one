## 0. 现状（量出来的，不是感觉）

| 事实 | 证据 |
|---|---|
| 全部 HTTP 走 `http.client`，一条连接一个请求 | `reconone/http.py:155` `Connection: close` |
| 抓取完全串行 | `crawl.py:106` 单 `while` 循环，逐个 `session.request()` |

结论：**瓶颈是"等待"而不是"计算"**。每个请求平均上百毫秒几乎全花在网络上，单线程意味着这些等待被完全串起来。这不是靠优化代码能解决的，是模型问题。

## 1. 选型

### 1.1 `httpx` —— 异步 HTTP 客户端（核心）

**解决**：并发抓取。`httpx.AsyncClient` 提供连接池 + HTTP/2 + 统一的超时/重试语义。

**为什么不自己写**：用 `asyncio` 裸写 TCP/TLS 等于重做一遍连接池、TLS 会话复用、分块解码、chunked 传输、代理支持。这是我们第 3 次想自己写的东西里最不值得的一次——它没有业务价值，只有 bug 风险。

**为什么不选 `aiohttp`**：也够好，但 `httpx` 的接口与现有 `requests`-风格代码几乎同构，迁移时 `Session.request()` 的调用点能机械替换；且它同时支持同步与异步两种模式，老代码可以继续跑。

**代价**：
- 新增 1 个直接依赖（`httpx` 依赖 `httpcore` + `certifi` + `idna` + `h11`，实际 5 个包）。
- 必须保留 `Session` 的**全部**既有纪律：作用域校验、字节预算、时间预算、证据记录。并发化最容易出的事故就是绕开这些闸门。

### 1.2 `anyio` —— 结构化并发原语（`TaskGroup`、`CapacityLimiter`）

**解决**：并发任务的生命周期与"限流"。

**为什么不自己写**：`threading.Thread` + 手写信号量在退出/异常路径上会漏线程。`anyio.TaskGroup` 保证「一个失败就取消同组其余任务」且「不会留下孤儿任务」。这正是批量探测需要的行为：第一个 401 出现时，剩下的 194 个请求应该立刻停，而不是继续打满 195 次。

**代价**：新增 1 个依赖（已在环境里）。它同时支持 asyncio 与 trio，将来换后端不用改业务代码。

### 1.3 `lxml` —— 【已移除，未采用】

原计划：用 `lxml` + `cssselect` 取 `html.parser` 拿不到的 DOM 关系（`form[action*="api"] input[name]`）。

**实际情况**：`reconone/` 内从未出现 `import lxml`（唯一导入点是本文件写下的设想），
`crawl.py` 一直用标准库 `html.parser`。声明了却不使用的依赖会让「零安装」承诺变成谎话，
因此已从 `requirements.txt` 删除。若将来真的要上 CSS 选择器，按 §4 的验收表重新引入。

### 1.4 明确**不**引入的

| 库 | 不引入的理由 |
|---|---|
| `aiohttp` | 与 `httpx` 功能重叠，二选一即可 |
| `requests` / `urllib3` | 只有同步能力，解决不了本任务的核心问题 |
| `uvloop` | 仅 Unix，Windows 远端用不了 |
| `playwright` / `selenium` | 需要浏览器二进制，与"只做被动静态读取"的定位冲突，且体积巨大 |
| `pydantic` | 报告 schema 已经用手写校验固定下来，换 `pydantic` 只会让「字段缺失」变成静默默认值——违反「不可验证标 unknown」 |
| `pandas` / `numpy` | 数据量是几百条，不是几百万条 |

## 2. 并发模型（这是重点，不是库本身）

引入库只是手段。真正要定的是**并发上限怎么来**。

```
并发度 = min(
    硬上限 8,                      # 对单个目标的最大并行请求数
    时间预算剩余 / 单请求超时,       # 别在截止前启动注定超时的请求
    字节预算剩余 / 单个响应上限
)
```

三条不可协商的规则：

1. **作用域闸门在并发层之前**。每个 URL 先过 `Session.in_scope()`，不过闸门的任务根本不进入任务组。禁止"先并发再过滤"。
2. **字节预算是共享原子量**。多个协程同时写 `bytes_total` 必须加锁，否则 40MB 上限会被突破 N 倍。
3. **失败不等于通过**。`TaskGroup` 里任何一个任务抛错，只取消该分支并把该项标 `unknown`，**不得**把整批结果判成 `fail`。这条直接对应 Task 11 的硬约束。

## 3. 验收方式

引入库不算完成，必须能证明它有效：

| 指标 | 基线（串行） | 目标 |
|---|---|---|
| 40 页抓取的墙钟时间 | 实测记录 | 至少 2× 提速 |
| 峰值内存 | 实测记录 | 不超过基线的 2× |
| 作用域越界请求数 | 0 | 仍然 0 |
| 字节预算突破次数 | 0 | 仍然 0 |
| 因并发引入的 `fail` 误判 | 0 | 仍然 0 |

达不到就回退，不留一个"引入了但没用"的依赖。
