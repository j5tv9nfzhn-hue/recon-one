# 为什么「维护水平 74」与「15 分钟打穿」同时成立

## 这是观测偏差，不是评分 bug 的一句话版本

我们的「维护水平」只读**未认证时可观测的浏览器侧配置**：响应头、Cookie 属性、TLS 版本、SPF/DMARC。
服务端鉴权、租户隔离、容器沙箱边界、业务逻辑——**这些信号一个都看不到**。

`free.ai` 的实测结果正好把这条边界摊开：

| 维度 | 本工具看到的 | 实际（人工实测） |
|---|---|---|
| HSTS | ✅ `max-age=31536000` | — |
| X-Frame-Options | ✅ `SAMEORIGIN` | — |
| X-Content-Type-Options | ✅ `nosniff` | — |
| Referrer-Policy | ✅ `same-origin` | — |
| COOP | ✅ `same-origin` | — |
| Cookie | ✅ Secure + HttpOnly + SameSite | — |
| TLS | ✅ 1.3 | — |
| SPF / DMARC | ✅ `-all` / `p=reject` | — |
| CSP | ❌ 缺失（唯一的大失分项） | — |
| **容器/沙箱隔离** | **不可观测** | ❌ 15 分钟越权 |
| **后端鉴权** | **不可观测** | ❌ 2 小时打穿 |

外围配置拿到的 43/58 分是真的；沙箱和后端被击穿也是真的。**两者不矛盾——它们测的根本不是同一层。**

## 为什么这个错误特别容易犯

因为「安全响应头齐全」和「应用安全做得好」在**统计上确实相关**，但相关的强度远不足以支撑个体判断。

- 响应头是**框架和 CDN 的默认值**。用 Next.js / Cloudflare / nginx 模板部署，头就齐了，跟团队的安全投入关系不大
- 反过来说，响应头齐全是**最低成本的合规动作**，它不能证明任何需要持续投入的能力（审计、隔离、权限模型）
- 更尖锐的一点：上次调研里那条「安全响应头有拼写错误的站点反而更脆弱」的结论，
  前提恰恰是**「管理员以为已经加固好了」**。头齐全但实现烂，是这个行业的常态而非例外

**结论：外围信号只能否证，不能证成。** 「头缺失」可以说明维护不足；「头齐全」不能说明维护良好。

## 已修正的三处

### 1. 判定不再从高分推出「放弃」

旧逻辑：
```python
if (h or 0) >= 70 and (o or 0) < 40:
    return "维护较好且成本不低，酌情放弃"   # ← 会亏钱的建议
```

新逻辑：**业务面优先，维护分永远不能单独否定一个目标**。
判定改成先看是否存在可承载测试的业务面：

```python
if write_eps >= 10 or len(surface) >= 3:
    return "worthwhile"      # 32 个写端点 + source map → 值得投入
```

`free.ai` 重算后的结论：

> **值得投入（存在实质业务测试面）** —— 观测到 32 个写方法端点、source map 可还原源码。
> 维护水平 74/100 只反映浏览器侧配置，**不能据此推断鉴权、租户隔离或沙箱边界的强度**。

### 2. 「可评估机会」低分是测量失败，不是目标没料

旧的机会轴把 `free.ai` 判为 32/100，因为它只认「能降低**我们**评估成本」的信号
（source map、明文凭据、公开规范、内部主机名）。这一轴测的是**工具能省多少力**，
不是**目标有多少可测面**。

而实测里真正的可测面很大：**32 个写方法端点**（旧逻辑因显式参数只有 7/195 = 4% 而给了 pass）。

已改为分开计分：

```
写方法端点 32 个；显式参数 7/195（4%）
```

并且说明落在证据里：**参数提取不到恰恰是「需要动态探测」的信号，不是「没有可测面」。**

### 3. 每个结论必须声明盲区

结论现在固定附一段「不覆盖范围」，GUI 面板底部、Markdown 报告、JSON 的
`score.triage.blind_spots` 三处都有。这不是免责声明，是**防止下一次误读的机制**。

## 对你实际判断的影响

| 你的判断 | 本工具能给的支持 | 边界 |
|---|---|---|
| 「这站外围很松」 | ✅ 可信，有原始响应头为证 | 仅外围 |
| 「这站有大量业务端点」 | ✅ 可信，来自 JS/规范提取 | 端点是否存在参数需实测 |
| 「这站维护好所以别打了」 | ❌ **本工具不支持这个推断** | 需实测鉴权与隔离 |
| 「这站值得打」 | ⚠️ 部分可信 | 只在观测到业务面时可下此结论 |

**一句话：本工具能告诉你「有没有入口」，不能告诉你「进去有多难」。**

## 顺带修掉的一个真 bug

`bool(script.get("sourcemap"))` 对字典永远为真——把「没有泄露」误判成「有泄露」。
该 bug 只影响 `assets.scripts` 走汇总路径时的判定，已修正并加回归测试。
